# Tech Debt

Known shortcuts and inefficiencies that are acceptable for now but should be revisited.

## Frontend

- **The "All" screen filter does not include deleted screens** (`frontend/src/utils/screenStatus.js`). The option keeps its empty value and therefore sends no `status` parameter, inheriting upstream's own default — the deny-list `status_id IS NULL OR status_id <> 3` — so it means "everything except deleted" while still being labelled "All". Accepted on 2026-09-24 because sending an explicit `active,inactive,deleted` allow-list instead would have hidden rows carrying a `NULL` or unmapped `status_id` with no option able to ask for them back, and because the deleted rows have their own entry directly beneath it.
  - Fix (if it ever confuses anyone): relabel the option "All except deleted", or add a fifth option that sends the explicit allow-list once a production `status_id` survey shows nothing else is in use.

- **One invalid legacy row fails the whole soft-delete batch** (`frontend/src/components/DeleteScreensModal.jsx`). The soft delete is a single all-or-nothing `PUT`, and upstream re-validates every field of every row where the hard `DELETE` validated none, so a screen that no longer passes current validation takes the rest of the selection down with it.
  - Three classes are caught client-side before sending (`partitionSoftDeletable`), because all three are decidable from the row already in hand: a row missing one of the ten *required* fields (a whitespace-only value in one of the five `@NotBlank` ones included); either direction of the `cpm`/`currency_code` gate; and the six bean-validation *bounds* on the same DTO (`lat` `±90.0`, `lon` `±180.0`, `player_id` `@Size(max = 255)`, `cpm` `@DecimalMin("0.0")`, `street` `@Size(max = 1024)`, `street_number` `@Size(max = 32)`, all inclusive). They fail identically at `@Valid` time, as a 400 keyed on the bare property name with no `dooh_settings[i]` index, so it names no screen. `utils/screenStatus.js` carries the upstream detail.
  - What remains needs an upstream lookup, or enforces a rule the annotation does not capture. **Attributable:** `PlacementDoohValidatorImpl` raises these as *indexed* `ErrorMessage`s (`dooh_settings[7].venue_type_tax`), which `labelBatchErrors` rewrites to `screen <id> (<player_id>) — <field>`, so the row can be unticked and the rest retried — an unresolvable or ambiguous `venue_type_tax`, an invalid `venue_type_id`, a non-URL `screen_img_url`, and `validatePositive`'s stricter `> 0` rule (`cpm`, `resolution_width`/`_height`, `venue_type_id`, `width`, `height`, `avg_weekly_audience`) alongside the duration rules. That last one is why a legacy row holding `cpm = 0` clears the `@DecimalMin("0.0")` pre-check and still fails the batch.
  - **Unattributable:** a `country_code` pointing at a country that is no longer `REGULAR_STATUS` is not a validator rule at all — `PlacementDoohConverter.applyScreenFields` throws `BadRequestApiException(country.not.found)` once validation has already passed, and `ExceptionHandlerController.createResponse` renders such an exception as a single `messages[]` entry with **no `property_name`**, hence no `dooh_settings[i]` index for `labelBatchErrors` to rewrite. The operator sees only the rejected country code and cannot tell which of up to 1000 selected screens holds it.
  - Ticking hard delete is not the way round any of this: it purges every screen that is ticked, not just the offending one, and that cannot be undone. Untick the named row, or repair the field in the screen's edit dialog, and retry.
  - Fix: fall back to per-row requests (or chunked batches) when a batch fails, at the cost of losing the all-or-nothing guarantee.

- **A soft delete writes back a snapshot taken at selection time** (`frontend/src/components/DeleteScreensModal.jsx`). The selection is a `Map<id, screen>` that deliberately survives paging, searching and filter changes, and the soft delete `PUT` is a full-row overwrite. A user who ticks rows on page 1, browses for a few minutes and then confirms therefore writes the pre-browse values of every field back over anything another operator changed in the meantime. This tab's own edit modal refreshes the snapshot on save, so only *concurrent* edits (another tab, another user, a bulk-upload job) are exposed, and the confirmation dialog says outright that confirming rewrites the stored values of these rows. The hard `DELETE ?ids=` this replaced carried ids only and had no such failure mode. Accepted on 2026-09-24 because the only faithful fix is re-fetching every checked row before building the body — up to 1000 sequential `GET .../dooh-settings/{id}` calls inside a click handler — and sending less is strictly worse: an omitted key becomes `NULL` upstream, so a minimal body would wipe `region`, `zip`, `street`, `street_number`, `device_id`, `cpm` and the rest.
  - Fix: re-fetch the checked rows in `handleConfirm` (ideally behind a bulk by-id read upstream does not currently offer), or add an upstream endpoint that patches `status` alone.

- **`client_max_body_size 8m` applies to the whole server block** (`frontend/nginx.conf`). It was raised for the 1000-row soft-delete `PUT`, but the file is installed as `/etc/nginx/conf.d/default.conf` inside the stock image's `http` block, so the server block is the only context the directive can sit in here — which means every route gets the 8 MB ceiling, including the multipart upload at `POST .../bulk-upload-jobs`, previously bounded by nginx's 1 MB default. Nothing is unbounded by it — `CreateJob` caps that route at `maxUploadBytes` (50 MB) with its own `http.MaxBytesReader`, and `proxyDoohSettings` at `handlers.DoohSettingsMaxBody` (8 MB, guarded by `TestProxyDoohSettings_RejectsOversizeBody`) — but nginx was the binding limit on the upload route, so a spreadsheet between 1 MB and 8 MB that used to be refused with a 413 at the edge now reaches Go and the SSP. Accepted on 2026-09-24 for the same reason as the timeout below: narrowing it means a second `location` block duplicating the proxy headers just for the DOOH settings path.
  - Fix: add a path-scoped `location` for `.../dooh-settings` carrying the larger body size and leave the server default at `1m`.

- **`proxy_read_timeout 300s` applies to the whole `/api/` location** (`frontend/nginx.conf`). It was raised for the 1000-row soft-delete `PUT`, but nginx applies it to every proxied call — login, reports, publishers — so a stuck upstream now pins each proxied connection for five minutes instead of one. `handlers/proxy.go` uses `http.DefaultClient` with no timeout of its own and `main.go` calls `http.ListenAndServe` with no `http.Server` timeouts, so nothing shorter bounds it. Accepted on 2026-09-24 because narrowing it means a second `location` block duplicating the proxy headers just for the DOOH settings path.
  - Fix: give `handlers/proxy.go` an `http.Client` with a per-request timeout (long only for the DOOH settings `PUT`), or add a regex `location` for that one path.

- **A soft delete recomputes the screen's `orientation`** (upstream `PlacementDoohConverter.applyScreenFields`; nothing in this repository controls it). `orientation` is `READ_ONLY` on the upstream DTO and `applyScreenFields` recomputes it from the submitted resolution on **any** `PUT`, whatever the body carries, so a legacy row whose stored orientation disagrees with its resolution is normalised as a side effect of being deleted. Harmless — the value is corrected, not corrupted — but it means the operation is not literally "change one column", and the row's history diff shows the extra field.
  - Fix: none available from this repository; it would take an upstream endpoint that patches `status` alone.

- **Copy VAST Tag is production-only** (`frontend/src/pages/PlacementDetail.jsx`). The ad host `https://ad.360yield.com` is hardcoded and does not follow the API environment switcher, so on acceptance the copied tag points at the production ad server while carrying acceptance publisher/placement IDs. The ad server is a different host from the API, which is why it was left out when the switcher landed (2026-09-24).
  - Fix: add an `adHost` field to each row of `API_ENVIRONMENTS` (`frontend/src/constants/apiEnvironments.js`) and build the URL from it.

- **Environment hosts are duplicated in the frontend** (`frontend/src/constants/apiEnvironments.js`). `api.360yield.com` / `api.360yielddev.com` are hardcoded for the login host note and the non-production accent strip, while the proxy resolves the real base URLs from `IMPROVE_API_BASE_URL` / `IMPROVE_ACCEPTANCE_API_BASE_URL`. Override either variable and the UI names a host the proxy is not using. Harmless for the default deployment (the values match `compose.yaml`), and the environment *label* — the actual safety signal — stays correct either way.
  - Fix: expose the resolved base URLs from the backend (e.g. on an existing GET) and render those instead of the constants.
  - Flagged by the code review of the environment switcher on 2026-09-24; not fixed because the alternatives were a new endpoint or dropping the most concrete cue from the accent strip.

- **Duplicate filter-change causes a wasted, aborted fetch** (`frontend/src/pages/PlacementDetail.jsx`, Screens tab). The page-reset effect (`useEffect(() => { setPage(1) }, [committedSearch, statusFilter])`) and the data-fetch effect (`useEffect(..., [publisherId, placementId, page, committedSearch, statusFilter, activeTab, screensTick])`) are separate. When a filter (search or status) changes while not on page 1, both effects fire in the same commit: the fetch effect runs first with the *new* filter but the *stale* `page`, issuing a request that's immediately aborted once `setPage(1)` triggers a re-render and the fetch effect re-runs with `page=1`. Net effect: one extra HTTP request per filter change while off page 1, always aborted before it's used.
  - Predates the status-filter addition (already present for the search filter); the status filter (added 2026-08-14) just extended it to a second trigger via the same existing pattern.
  - Fix: merge the two effects, or reset `page` synchronously within the fetch effect when a filter changed, so only one request fires per filter change.
  - Flagged by the `/simplify` efficiency review on 2026-08-14; not fixed because doing so properly means restructuring both effects, which affects existing search-filter behavior too and was out of scope for that change.
